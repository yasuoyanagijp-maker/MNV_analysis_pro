### 送付メール本文の必須項目（順序）

1. 挨拶・文脈
2. **ダウンロード URL**（公開配布ページ）

4. **ログイン情報**
5. 解析モード（MNV が通常。VD 希望時は VD を強調）

### 添付 ZIP の選び方

| 相手の環境 | 添付ファイル |
|-----------|-------------|
| Mac（Apple Silicon / M1/M2 等） | `ARIAKE_OCTA_mac.zip` |
| Mac（Intel） | `ARIAKE_OCTA_macOS_Intel_v1.2.1.zip`（Releases の v1.2.1-mac 内） |
| Windows | `ARIAKE_OCTA.zip`（v1.2.1-win） |
| Mac + Windows 両方 | 上記2種（または3種）を添付 |

**Intel Mac の注意**: Apple Silicon 版は Intel Mac で起動不可（`incorrect executable format`）。必ず Intel 版を送る。

## 3. 送付先 ID の付け方

- 新規の先生には **連番 ID** を付与（現在の最大 ID + 1）。
- **To / CC グループ**は別 ID で登録し、備考に「002 の CC」等と相互参照する。
- 同一施設・同一メールで Mac+Win を送る場合は **1 ID** で `送付OS: Mac + Windows` とする。
- ID を統合した場合は「ID: 016 は 015 に統合済」と明記する。

### ステータス表記（推奨）

| ステータス | 意味 |
|-----------|------|
| OS確認メール文案作成済 | まだ OS 未確認・未送付 |
| 送付準備中 | OS 確認済・これから送付 |
| 送付完了 | ZIP 送付済・利用報告なし |
| 送付完了・使用中 | 起動 or 解析成功の返信あり |
| 再送準備中 | リンク切れ・不具合等で再送予定 |

## 4. 応対フロー（シナリオ別）

### 4-A. 新規の配布依頼を受けたとき

```
[依頼メール受信]
    ↓
① 配布送付先・履歴.txt を開き、同姓同名・同施設がないか検索
    ↓
② 新規なら ID を採番し【送付先一覧】に登録
    ↓
③ OS が不明なら → 4-B（OS確認メール）
   OS が判明していれば → 4-C（初回送付）
```

**登録時に書く項目**: 氏名、所属、メール、CC、送付OS、主な用途、文脈、備考、ステータス

---

### 4-B. OS 確認メール（未送付・OS 不明）

**件名例**: OCTアンギオ血管解析ソフトのご送付について

**本文の要点**:
- 使用予定の PC が **Mac か Windows か**（両方なら両方）を教えてほしい
- Mac の場合は **Apple Silicon か Intel か** も分かれば助かる

**送付後の記録**:
- ステータス: `OS確認メール文案作成済` または `送付準備中`
- 【送付履歴】にはまだ書かない（返信待ち）

**返信例の解釈**:
- 「普段 Mac、大学 OCT は Windows」→ **Mac + Windows 両方送付**
- 「MacBook Air M1」→ **Mac（Apple Silicon）**
- 「MacBook Pro 2020」→ **Intel 版を確認**（年式・チップを必ず聞く）

### 4-D. 返信を受けたとき（起動確認・お礼・研究報告）

| 返信の内容 | 対応 |
|-----------|------|
| 起動・ログイン成功 | ステータス → `送付完了・使用中`。履歴に「〇〇確認の返信受領」 |
| 解析成功 | 同上。フォルダ指定で解決した場合は備考に記録 |
| お礼のみ | 返信は任意。短いお礼で可 |
| 研究相談・統計の質問 | 送付履歴に相談内容を要約。別途返信（研究対応） |
| 再送・URL 不具合依頼 | → 4-E |

**返信不要なことが多い**: 起動確認のお礼は、履歴更新のみで十分な場合が多い。

### 4-E. 再送（リンク切れ・URL 不具合）

**原因の典型**:
- 本体リポジトリが private 化され旧 URL が 404
- 簡易マニュアル内の相対リンク `USER_MANUAL.md` が PDF では機能しない

**対応**:
1. **公開配布 URL** を案内（`ARIAKE_OCTA-distribution`）
2. 必要なら ZIP を **メール添付**でも再送
3. 履歴に「再送」「URL不具合」を記録
4. ステータス: `再送準備中` → 送付後 `送付完了`

**寺尾先生型（Mac+Windows・CC あり）**:
- To: 主担当、CC: 共同研究者
- 両 OS の ZIP + 公開 Releases URL + マニュアル URL

### 4-F. トラブルシューティング（よくある問い合わせ）

#### 症状: Confirm Selection 後に最初の画面に戻る

**原因**: 画像ファイルを1枚ずつ選んでいる  
**案内**（送付メールにも必ず記載）:

1. 新しいフォルダを作成
2. 解析したい画像をフォルダに入れる
3. アプリで **フォルダ単位** で選択し Confirm Selection
4. ImageJ 変換は通常不要

**実績**: 鎌尾先生（ID:007）— フォルダ指定で解決（2026-07-03）

---

#### 症状: Mac で「incorrect executable format」

**原因**: Apple Silicon 版を Intel Mac で実行  
**対応**: `ARIAKE_OCTA_macOS_Intel_v1.2.1.zip` を再送。別 PC でビルドした Intel 版が有効だった事例あり（木住野先生 ID:004）

**補足**: Intel Mac 初回起動は 90 秒程度かかることがある

---

#### 症状: メールがバウンス

**対応**:
- 履歴の「正」メールと「旧・エラー」メールを分けて記録
- 学会・MR 経由で正アドレスを確認（瀧澤先生: b7→a8）

---

#### 症状: ログインで「Connection Error: All connection attempts failed」

**原因（認証失敗ではない）**: ログイン画面の UI は出ているが、同じ PC 内の解析エンジン（FastAPI / `127.0.0.1`）に届いていない。

| 見分け | 典型 |
|--------|------|
| **Mac（とくに macOS 26）** | 配布 ZIP が **ad-hoc・未公証**。親プロセス（ログイン画面）は残るが、解析エンジンの **子プロセスがコード署名違反（CODESIGNING Invalid Page）で殺される**。ネットを変えても直らない |
| **病院・電子カルテ用 Windows** | ファイアウォール／エンドポイント対策がローカル待受を遮断（尾花先生施設と同型） |

**案内**:

1. 入力（ローマ字名 / `ariake2024` / 自施設コード）は正しいことが多い、と先に伝える
2. **Mac でクラッシュレポートに `CODESIGNING` / `Invalid Page` がある** → 本人の操作ミスではない。**公証は不要。** ターミナルで次を実行（または新しい `インストール.command` で上書きインストール）:
   ```
   xattr -cr /Applications/ARIAKE_OCTA.app
   codesign --force --deep --sign - /Applications/ARIAKE_OCTA.app
   open /Applications/ARIAKE_OCTA.app
   ```
   それでもダメなら当面は **Windows 版**。根本の配布物はアドホック再署名＋エンジンをスレッド起動する版を案内
3. Mac でクラッシュレポートが無い場合は、`インストール.command` 経由・`xattr -cr` を案内
4. 病院の業務用 Windows だけ失敗するなら、研究用 PC へ誘導（IT 例外より早い）

**実績**:
- 瀧澤先生（ID:005、東北大学）— 2026-08-27。M1 MacBook Air / macOS 26.5。自宅・病院・テザリングすべて失敗。クラッシュは子プロセス `CODESIGNING Invalid Page`（親 60050 → 子 60052、起動約7秒後）。**Windows 版は動作**
- 尾花先生施設 — 業務用 Windows のファイアウォールでローカルエンジン接続失敗。研究用端末へ誘導

---

#### 症状: Windows で exe が起動しない

**確認項目**:
- ZIP を展開した `ARIAKE_OCTA` フォルダごと使っているか（`_internal` 同階層）
- SmartScreen →「詳細情報」→「実行」
- **病院・電子カルテ用 PC の場合** → IT にファイアウォール例外を頼むより、**研究用の個人ノートで使う**よう案内（ログイン Connection Error と同じ）

## 6. GitHub 公開配布の運用

詳細は `documentation/DISTRIBUTION_REPO.md` を参照。

### 構成

| リポジトリ | 公開 | 内容 |
|-----------|------|------|
| `MNV_analysis_pro` | private 推奨 | ソース・ビルド |
| `ARIAKE_OCTA-distribution` | **public** | ZIP（Releases）・マニュアル |

### 日常運用

1. 本体でビルド → `MNV_analysis_pro` に Release publish
2. GitHub Actions（`Sync distribution repo`）が配布リポへミラー
3. 配布メールでは **distribution の Releases URL** を案内

### PAT（`DISTRIBUTION_SYNC_TOKEN`）とは

Actions が **別リポジトリへ書き込むためのトークン**。  
`MNV_analysis_pro` → Settings → Secrets → `DISTRIBUTION_SYNC_TOKEN` に Fine-grained PAT を登録。

### 手動同期（Actions が動かないとき）

```bash
cd /path/to/MNV_analysis_pro
export GH_TOKEN="（PAT）"
./.github/scripts/sync-distribution.sh

# Release もミラーする場合
SYNC_RELEASE=true RELEASE_TAG=v1.2.1-mac ./.github/scripts/sync-distribution.sh
SYNC_RELEASE=true RELEASE_TAG=v1.2.1-win ./.github/scripts/sync-distribution.sh
```

## 8. Cursor / AI を使うとき

チャットで「配布依頼の返信文案」「〇〇先生の履歴更新」と依頼する場合:

1. ルール `distribution-email.mdc` が参照される（未設定なら本手順書を `@` で指定）
2. AI は `配布送付先・履歴.txt` と `配布依頼メールテンプレート.txt` を正とする
3. **出力はプレーンテキスト**（Gmail 貼り付け用。Markdown 表は使わない）
4. 送付後は必ず人間が履歴を確認・コミットする

**依頼文の例**:
- 「飯田先生 OS 確認返信を受けた。履歴更新と Mac+Win 送付メールをテンプレ通り作成」
- 「鎌尾先生の解析成功返信を履歴に追加」
- 「寺尾先生へ再送。CC 津須先生。URL 案内版」
